# SeatOps 두 페이즈 학습·개발 계획

**계획만 작성된 상태입니다. 아래 기능·파일·명령은 앞으로 만들 대상이며 현재 실행 가능한 프로젝트를 뜻하지 않습니다.**

기존 2026-11-16~11-27의 10영업일 일정은 초기 참고 일정입니다. **Phase 1을 직접 완성하고 설명할 수 있게 된 뒤 Phase 2의 시작 날짜를 확정합니다.** 달력상 배포 날짜가 되었다고 미완성 서비스를 AWS로 옮기지 않습니다.

하루 최대 60~90분 과제 두 개와 복습 30분을 기준으로 하되, 실제로는 한 번에 과제 하나만 제공합니다. 검증·개념 확인에 시간이 더 들면 뒤 날짜를 이동합니다. 처음 배우는 기술이 많으므로 전체를 2주 안에 끝내는 것은 보장하지 않습니다.

| 페이즈 | 핵심 질문 | 완료할 결과 | 범위 |
|---|---|---|---|
| **Phase 1: SeatOps 자체 만들기** | 내 컴퓨터에서 서비스가 제대로 동작하는가? | AWS 없이 생성→원본→검증→집계, 중복 방지·오류 수정·테스트가 되는 로컬 MVP | Python, SQL, PostgreSQL, pytest, 로컬 Docker Compose, 기본 CI |
| **Phase 2: 배포하며 클라우드 배우기** | 완성한 서비스를 AWS에서 안전하게 실행·관측·복구할 수 있는가? | 동일 서비스의 EC2 실행, S3 연결, 권한·네트워크·로그·복구 증거 | AWS, Terraform, CloudWatch, 배포 절차와 인프라 CI |

여기서 SeatOps 서비스는 가상 이벤트를 처리하는 데이터 플랫폼을 뜻합니다. 별도 예약 웹 UI/API를 추가하는 계획은 아닙니다. Phase 1의 입력은 로컬 JSONL, Phase 2에서 S3 입력을 연결합니다. **서비스 자체의 기능 완료와 클라우드 운영 완료를 별도로 인정합니다.**

## 시작점 진단

현재 존재하는 제품 관련 파일은 README.md, 01_mvp_scope.md와 학습자의 preview_test.py입니다. 진단 풀이에는 event_id 조건으로 정상/오류를 나누는 함수와 assert가 있습니다. 실제 생성기·DB·Docker·CI·AWS는 없습니다.

첫 학습은 기존 풀이 리뷰에서 이어갑니다. Python/SQL 진단 답을 받기 전에 프로젝트 구현 파일을 만들지 않습니다. 이미 설명할 수 있는 개념은 건너뛰고, 설명은 되지만 작성이 막히는 부분에는 함수 입출력·작은 힌트를 제공합니다.

## Phase 1 · SeatOps 자체 완성

아래 Day 1~5는 학습 순서이며 고정 마감일이 아닙니다. 로컬 Docker는 실행 환경을 맞추기 위한 도구이고 AWS 배포는 시작하지 않습니다.

### Day 1 — 진단과 범위 이해

- **과제 A, 60분:** 기존 preview_test.py를 설명하고 입력 변경 여부·빈 입력·잘못된 타입을 스스로 확인한다. 미응답 Python/SQL 진단을 제출한다. 정답은 미리 받지 않는다.
- **과제 B, 60분:** Raw/Staging/Quarantine/Mart 역할과 이벤트 필드 후보의 의미를 자기 말로 적는다. 이 과제는 A의 개념 확인 후 진행한다.
- 개념: 함수 입출력과 가변 객체, SELECT/WHERE/GROUP BY, 데이터의 한 행을 뜻하는 Grain.
- 예정 파일: 기존 `preview_test.py`, 필요 시 본인이 작성하는 `docs/learning-log.md`.
- 검증: `python3 preview_test.py`; SQL 답안은 쿼리와 예상 결과를 함께 설명한다.
- 완료: 진단 결과가 확인되고 아직 모르는 부분과 MVP 제외 범위를 설명한다.
- 예상 어려움: 이해한 내용을 빈 파일에서 코드로 옮기는 것. 입출력 한 쌍부터 쓴다.
- 면접 설명: 예약 서비스 대신 이벤트 처리 시스템을 만드는 이유, 클라우드 학습으로 우선순위를 바꾼 이유.

### Day 2 — 이벤트 생성과 JSONL

- **과제 A, 60~90분:** 필드 타입·필수 여부·정상 이벤트 한 개를 직접 설계하고 생성 함수 초안을 쓴다.
- **과제 B, 60~90분:** seed와 기준 날짜를 입력으로 받아 작은 파일을 저장하고 정상·오류 fixture를 만든다.
- 개념: dict/list, 함수 분리, random seed, 시간대, JSON과 JSON Lines의 차이.
- 예정 파일: 생성기 모듈 하나와 대응하는 테스트 하나. 파일명·함수명은 리뷰에서 결정한다.
- 검증: 환경을 준비한 뒤 `python -m pytest -q`; 같은 입력으로 생성한 두 파일의 바이트를 비교한다.
- 완료: 같은 seed·날짜·옵션은 같은 데이터. 모든 필드의 의미를 본인이 설명한다.
- 예상 어려움: 현재 시각·UUID가 재현성을 깨는 문제. 어떤 값을 입력으로 받아야 하는지 직접 판단한다.
- 면접 설명: 테스트 데이터 재현성이 장애 재현에 필요한 이유.

### Day 3 — PostgreSQL과 Raw 적재

- **과제 A, 60~90분:** Raw의 Grain·원본 보존 방식·PK/Unique 후보를 작성한다. 리뷰 후 최소 DDL을 직접 쓴다.
- **과제 B, 60~90분:** 로컬 PostgreSQL에 작은 파일을 적재하고 입력/저장 건수를 검증한다. DB 컨테이너 설정은 필요한 만큼만 함께 준비한다.
- 개념: PK와 Unique, 트랜잭션, JSONB와 원본 문자열/바이트, SQL 파라미터 바인딩.
- 예정 파일: 최소 DB Compose 설정, 스키마 SQL, 적재 함수와 통합 테스트.
- 검증: DB가 준비되면 `docker compose up -d db`; 직접 작성한 count/중복 조회 SQL과 pytest 실행.
- 완료: 원본이 보존되고 같은 파일의 두 번째 적재로 중복이 증가하지 않는다.
- 예상 어려움: 이벤트 ID와 원본 행 ID 혼동, DB 비밀번호/접속 설정.
- 면접 설명: 원본 식별과 업무 이벤트 중복 판별을 구분하는 이유.

### Day 4 — 검증·격리·Mart

- **과제 A, 60~90분:** 가장 중요한 품질 규칙 3개부터 직접 정의하고 정상/오류 분리·원인 저장을 구현한다.
- **과제 B, 60~90분:** Mart Grain과 성공률 계산식을 정하고 집계 SQL·중복 재실행 테스트를 쓴다.
- 개념: 검증과 변환의 경계, 오류 코드, 집계 분모, NULL/0 나누기, 트랜잭션 rollback.
- 예정 파일: 검증 모듈, 품질 규칙 기록, Staging/Quarantine DDL, Mart SQL, 테스트.
- 검증: `python -m pytest -q`; 정상·오류·동일 ID 충돌·분모 0 사례를 확인한다.
- 완료: 오류가 Staging에 없고 같은 입력 재실행 후 Mart가 같다. 규칙이 늘어나면 이 날짜를 연장한다.
- 예상 어려움: 정상/오류/중복 건수 중복 계산, 동일 ID의 다른 내용 처리.
- 면접 설명: 성공률의 정확한 분모와 멱등성 보장 근거.

### Day 5 이후 — 로컬 실행과 Phase 1 마무리

- **과제 A, 60~90분:** 앱 Dockerfile·Compose 환경변수·DB volume을 이해하며 직접 조립한다.
- **과제 B, 60~90분:** 생성→적재→검증→Mart를 실행하고 성공/실패 로그·처리 건수·실행 이력을 확인한다.
- **후속 과제 C, 60~90분:** 오류 수정 재처리와 원본·수정 이력 보존을 직접 구현·테스트한다.
- **후속 과제 D, 60~90분:** 로컬 중간 실패·강제 종료·재실행·DB 재시작 후 데이터를 비교한다.
- **후속 과제 E, 60~90분:** GitHub Actions에 pytest와 앱 이미지 빌드 검증을 추가하고 로컬 실행 README를 작성한다.
- B 이후 과제는 다음 학습일로 넘긴다. 한 번에 하나씩 수행하며 AWS 단계 시작일도 그만큼 이동한다.
- 개념: 이미지/컨테이너/볼륨 수명, 내부 DNS, 프로세스 종료와 DB 트랜잭션.
- 예정 파일: Dockerfile, Compose, 환경변수 예시, 실행 이력·재처리 로직·통합 테스트, 기본 CI workflow, 로컬 README.
- 검증: 해당 파일을 만든 뒤 `docker compose build`, `docker compose up -d`, pytest; DB 재시작 전후 건수 비교.
- 완료: 로컬 전체 흐름, 원본 보존, 오류 수정 이력, 중복 없는 재시도가 확인된다.
- 예상 어려움: 호스트/컨테이너 경로·권한, 이미 적재한 데이터로 실패 실험을 해버리는 문제.
- 면접 설명: restart와 volume 삭제의 차이. 완료되지 않으면 AWS 단계보다 먼저 보완한다.

### Phase 1 종료 조건 — 전부 확인한 뒤 배포 학습 시작

- [ ] AWS 계정이나 S3 없이 로컬 JSONL부터 Mart까지 실행한다.
- [ ] 정상/오류/중복 입력과 수정 재처리를 테스트한다.
- [ ] 부분 실패·강제 종료·DB 재시작 후 재실행해도 결과가 중복되지 않는다.
- [ ] 성공/실패·처리 건수·실행 이력을 로컬에서 확인한다.
- [ ] pytest 및 기본 CI가 통과하고 README로 로컬 실행을 재현한다.
- [ ] 학습자가 데이터 흐름·중복 키·원본 보존·트랜잭션을 설명한다.

이때 **SeatOps 로컬 MVP 완성**으로 기록한다. AWS 검증이 없다는 이유로 서비스 자체가 미완성인 것은 아니다. 이 기준을 통과하기 전에는 Terraform·AWS 구현을 진행하지 않는다.

## Phase 2 · 완성한 SeatOps 배포와 운영

아래 Day 6~10은 기존 순서 이름만 유지하며 실제 날짜는 Phase 1 완료 후 배정한다. 서비스 핵심 로직을 다시 만들지 않고 배포 설정과 S3 입출력 연결을 추가한다.

### Day 6 — AWS 네트워크·IAM·Terraform

- **과제 A, 60~90분:** VPC→Subnet→Route→IGW와 SG를 직접 그린다. SSM 접속 및 EC2 역할의 권한 초안을 쓴다.
- **과제 B, 60~90분:** 작은 Terraform 리소스부터 순차 작성하고 변수·state·보안 검증을 추가한다.
- 개념: CIDR, public subnet과 inbound 개방의 차이, IAM 신뢰 정책/권한 정책, Terraform state.
- 예정 파일: `infra/terraform/`의 최소 구성·변수·모의 테스트. 한꺼번에 전체 코드를 받지 않는다.
- 검증: 준비 후 `terraform fmt -check`, `terraform init -backend=false`, `terraform validate`; 자격증명 없는 모의 테스트.
- 완료: 각 리소스의 필요성과 외부에서 DB에 접근할 수 없는 이유를 설명한다.
- 예상 어려움: IAM·SG·route의 역할 혼동, state에 민감정보가 남는 문제.
- 면접 설명: EC2 role을 쓰는 이유와 작은 구성에서 NAT Gateway를 생략하는 장단점.

### Day 7 — 승인 후 EC2·S3 연결

- **과제 A, 60~90분:** 계정·리전·비용·Terraform plan을 검토한다. 승인받은 뒤에만 apply하고 SSM 접속을 확인한다.
- **과제 B, 60~90분:** 로컬에서 검증한 이미지로 EC2에서 실행하고 S3 원본 업로드/다운로드를 연결한다.
- 개념: 임시 자격증명, instance profile, S3 object key, 이미지 아키텍처·동일 이미지 배포.
- 예정 파일: S3 입출력 모듈·테스트, AWS용 실행 설정, 배포 작업 기록.
- 검증: 승인 후 `terraform plan`, `terraform apply`, `aws ssm start-session`; S3→DB 건수 확인.
- 완료: 실제 입력을 S3에서 읽어 정상·오류·집계를 확인하고 증거를 기록한다.
- 예상 어려움: ARM Mac/EC2 이미지 차이, IAM AccessDenied, container에서 역할 자격증명 접근.
- 면접 설명: Access Key 하드코딩 없이 인증되는 경로. 승인/계정이 준비되지 않으면 로컬 모의 테스트까지만 완료한다.

### Day 8 — 기존 실행 로그를 CloudWatch에서 관측

- **과제 A, 60~90분:** Phase 1에서 만든 성공/실패 로그·처리 건수·실행 이력을 CloudWatch로 전달하는 방법을 이해하고 연결한다.
- **과제 B, 60~90분:** 승인된 AWS 환경에서 CloudWatch 수집과 오류 검색·최소 알람을 확인한다.
- 개념: 이벤트 발생 시각과 처리 소요 시간, 로그/지표/알람의 차이, 로그 보존 기간.
- 예정 파일: CloudWatch·로그 수집 설정, AWS 운영 기록. 기존 실행 이력과 로그 형식은 재사용한다.
- 검증: 성공과 의도적 실패를 실행해 실제 log stream·run_id·건수·알람 상태 확인.
- 완료: 오류 원인과 해당 실행을 찾을 수 있다. 직접 확인하지 않은 AWS 로그는 완료로 기록하지 않는다.
- 예상 어려움: 앱 오류와 로그 드라이버 오류 구분, 동일 실패의 이중 집계.
- 면접 설명: Quarantine 건수와 배치 실행 실패 건수가 다른 이유.

### Day 9 — 인프라 검증 추가와 AWS 장애 복구

- **과제 A, 60~90분:** Phase 1의 기본 CI에 Terraform 검증을 추가하고 테스트가 실패하면 배포하지 않는 절차를 정한다.
- **과제 B, 60~90분:** 로컬에서 검증한 중단·재실행 실험을 승인된 EC2에서도 수행하고 S3·IAM·네트워크 장애 진단 절차와 AWS Runbook을 작성한다.
- 개념: 변경 검증과 배포의 차이, CI gate, 실행 중단 상태와 rollback, 재시도.
- 예정 파일: workflow 하나, 복구 검증 테스트/스크립트, `docs/RUNBOOK.md`.
- 검증: GitHub Actions 실행 URL, 실패시키는 변경에서 check 실패 확인, 강제 종료 전후 SQL 비교.
- 완료: 정상뿐 아니라 실패 검증이 통과하고 본인이 로그로 원인을 설명한다.
- 예상 어려움: 로컬에서만 통과하는 테스트, 기존 볼륨을 실수로 지우는 복구 절차.
- 면접 설명: 테스트 실패 시 배포가 차단되어야 하는 이유. 자동 CD는 선택 과제다.

### Day 10 — AWS 운영 증거·비용·포트폴리오 정리

- **과제 A, 60~90분:** 수용 기준을 코드·테스트·실제 실행 기록과 대조하고 부족한 항목을 표시한다.
- **과제 B, 60~90분:** 직접 내린 결정·실패 경험·복구 근거로 README/ADR/면접 설명을 작성한다. 필요 증거 백업 후 승인된 리소스만 정리한다.
- 개념: 운영 주장과 증거, EC2/EBS/IPv4/S3/로그 비용, versioned bucket 삭제, 데이터 내구성.
- 예정 파일: README, ADR, 검증 기록, 비용 기록, Runbook.
- 검증: 최종 pytest/CI, 실제 배포 증거, 승인 후 `terraform plan -destroy`와 `terraform destroy`, 잔존 리소스 확인.
- 완료: 구현/미구현이 분리되고 실제 수행한 범위만 자기 경험으로 설명한다.
- 예상 어려움: stop만으로 비용이 모두 없어졌다고 오해, S3 이전 버전 잔존.
- 면접 설명: 비용·복구·보안에서 선택한 절충안과 다음 확장 조건.

## 매 과제의 고정 형식

‘이번 작업 / 필요한 개념 / 내가 먼저 결정할 것 / 구현 과제 / 완료 조건 / 검증 방법 / 개념 확인 질문 2~3개 / 다음 단계 조건’을 사용한다. 과제 제출물은 짧은 코드·실행 결과·본인 설명이다. AI는 먼저 힌트를 주며 두 번 이상 막히거나 명시적 요청이 있을 때만 전체 예시를 제공한다.

## 일정 조정 규칙

완료 조건 또는 개념 확인이 미충족이면 해당 과제에서 멈추고 이후 날짜를 이동한다. 10일은 보장 일정이 아니다. 일정을 맞추기 위해 핵심 구현을 AI에 넘기거나 미검증 항목을 완료로 처리하지 않는다. ECR 자동 CD·RDS·Airflow는 필수 과제가 안정된 뒤, 해결할 한계를 확인했을 때만 별도로 계획한다.
